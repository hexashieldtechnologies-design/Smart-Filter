मैंने इसमें खास तौर पर ये चीजें रखी हैं:

* App update के बाद existing local data **delete न हो**
* PhonePe-जैसा **device biometric/PIN authentication**
* Fingerprint/PIN app खुद store न करे; Android system authentication इस्तेमाल हो
* Aadhaar/PAN/document images **server database में नहीं**, encrypted local vault में रहें
* Android Keystore से encryption keys protect हों
* Root/compromised device पर app **block** हो
* Smart Fill locked vault से sensitive data access न कर सके
* Production में hidden bypass न हो

````markdown
# Secure Local Vault + App Lock + Root Detection
## Flutter / Android Developer Specification

### Scope

Modify the existing Flutter application.

DO NOT rebuild the entire application.

This specification adds a security layer for:

1. App Lock
2. Fingerprint / Face / Device PIN authentication
3. Encrypted local document storage
4. Android Keystore key protection
5. Secure app-update data persistence
6. Root / compromised-device detection
7. Smart Fill security integration

---

# 1. MAIN REQUIREMENT

The application contains sensitive personal documents such as:

- Aadhaar
- PAN
- Passport
- Driving Licence
- Personal profile information
- Phone number
- Email
- Address
- Date of birth
- OCR-extracted information

These must be treated as highly sensitive data.

The primary sensitive document storage should be:

> ENCRYPTED LOCAL DEVICE STORAGE

NOT an ordinary backend database.

---

# 2. APPLICATION STARTUP FLOW

Implement this startup sequence:

```text
App Launch
    ↓
Device Integrity Check
    ↓
Is device rooted / compromised?
       ↓
   YES → Block application
       ↓
      NO
       ↓
Initialize Secure Storage
       ↓
Check App Lock
       ↓
Android Biometric / Device Credential
       ↓
Authentication Successful
       ↓
Unlock Secure Vault
       ↓
Open Home Screen
````

The user must never see sensitive documents before authentication.

---

# 3. PHONEPE-LIKE APP LOCK

The application should provide an experience similar to secure financial applications.

Example:

```text
        🔒

   Secure Vault Locked

Authenticate to continue

      [Fingerprint]

Use device PIN / Password
```

The app must use Android's native authentication system.

Use:

```text
Android BiometricPrompt
```

with device credential fallback where supported.

---

# 4. IMPORTANT AUTHENTICATION RULE

The application must NOT store:

* fingerprint data
* fingerprint templates
* Face ID/face templates
* Android device PIN
* Android device password
* biometric credentials

The Android operating system performs the authentication.

The application only receives a success/failure result.

Architecture:

```text
Flutter
   ↓
BiometricAuthService
   ↓
Android BiometricPrompt
   ↓
Fingerprint / Face / Device Credential
```

---

# 5. FIRST-TIME SETUP

On first setup:

```text
Create Account
      ↓
Create Secure Local Vault
      ↓
Ask:
"Enable biometric unlock?"
      ↓
Android authentication
      ↓
Enabled
```

If biometric authentication is unavailable, allow the supported Android device-credential fallback.

Do not create a fake fingerprint screen.

---

# 6. APP OPEN FLOW AFTER SETUP

Every time the protected application is opened:

```text
Open App
   ↓
Security Check
   ↓
Authentication Screen
   ↓
Fingerprint / Face / Device Credential
   ↓
Success
   ↓
Secure Vault unlocked
   ↓
Home
```

If authentication fails:

```text
Authentication failed.

Please authenticate to continue.
```

Do not show sensitive information.

# 7. BACKGROUND / MINIMIZE BEHAVIOR

```text
       ↓
App goes to background
       ↓
Sensitive screen becomes protected
       ↓

       ↓
```

For maximum-security mode:

```text
Background
    ↓
Immediately lock
```

```text
        ↓

```

```text

```

# 12. IDENTITY DOCUMENT IMAGES

# 13. LOCAL VAULT STRUCTURE

Recommended conceptual structure:

```text
App Private Storage
│
└── encrypted_vault/
    │
    ├── documents/
    │   ├── random-id-001.enc
    │   ├── random-id-002.enc
    │   └── random-id-003.enc
    │
    └── database/
        └── encrypted-vault.db
```

Use random identifiers.

BAD:

```text
aadhaar_ANAM.jpg
PAN_ABCDE1234F.jpg
```

GOOD:

```text
document_82a91.enc
document_b31f7.enc
```

Never put sensitive information in filenames.

---

# 14. DOCUMENT ENCRYPTION

Before writing a document to storage:

```text
Document
   ↓
Encrypt
   ↓
Encrypted bytes
   ↓
App-private storage
```

Use a standard authenticated encryption mechanism such as AES-GCM through a maintained cryptographic library.

Do NOT invent custom encryption.

Do NOT use:

```text
hardcoded password
hardcoded encryption key
```

---

# 15. ANDROID KEYSTORE

Encryption keys must be protected using:

```text
Android Keystore
```

Architecture:

```text
Android Keystore
       ↓
Protect vault key
       ↓
Vault key
       ↓
Decrypt encrypted local database/files
```

Never store the master encryption key in:

```text
Dart source code
SharedPreferences
JSON
Plain SQLite
constants
Git repository
```

---

# 25. ROOT DEVICE DETECTION

Create:

```text
DeviceIntegrityManager
```

It must check whether the device appears rooted, compromised, tampered with, or otherwise fails the application's security policy.

Do NOT rely on a single root check.

Use multiple signals.

Possible checks:

```text
Root-management indicators
Known root binaries
Suspicious executable paths
Writable protected directories
Suspicious system properties
Build/test-key indicators
Debugger/tampering indicators
Application integrity
Play Integrity where applicable
```

Use maintained security libraries when appropriate.

---

# 26. ROOTED DEVICE STARTUP

At startup:

```text
Device Integrity Check
       ↓
Safe?
    /     \
  YES      NO
   ↓        ↓
Continue   Block
```

If the device fails the application's security policy:

```text
This device does not meet the
security requirements of this application.

For your protection, the secure vault
cannot be opened on this device.

[Close App]
```

The application must not show:

* documents
* Aadhaar
* PAN
* Smart Fill data
* profile information

before this check completes.

# 27. PLAY INTEGRITY

For production Android builds, consider integrating:

```text
Google Play Integrity
```

Use it as an additional security signal.

Architecture:

```text
Local Integrity Checks
        +
Play Integrity
        +
App Signature / Installation Integrity
        ↓
DeviceIntegrityManager
```

Where server-side validation is needed, verify the Play Integrity token on the backend.

Do NOT trust a client-side value such as:

```text
isRooted = false
```

as the only security mechanism.

---

# 28. ROOT DETECTION LIMITATION

Root detection is not perfect.

Do not claim:

```text
100% root detection
```

Instead use layered security:

```text
Root detection
+
Play Integrity
+
Android Keystore
+
Biometric/device authentication
+
Encrypted storage
+
Minimal data exposure
```

# 29. PRODUCTION BYPASS

Production builds must NOT contain:

```text
Secret PIN
Hidden button
Magic code
Developer password
Root bypass
Debug endpoint
```

A development-only override may exist in a separate local debug configuration, but it must not be accessible in production.

```text
       ↓

       ↓
```

```text

PAN image

Complete document vault
```

# 32. SECURE MEMORY HANDLING

# 35. LOGOUT VS APP LOCK

These must be separate.

### App Lock

```text
Temporary protection
      ↓
Biometric/device authentication
      ↓
Vault available again
```

### Logout

```text
Clear authenticated account session
      ↓
Lock vault
      ↓
Require account login again
```

Do NOT automatically delete local documents on logout.

---

# 36. UNINSTALL

Sensitive data should remain inside app-private storage.

Normally:

```text
Uninstall
    ↓
Android removes app-private storage
    ↓
Local vault removed
```

Do not copy sensitive documents to public storage just so they survive uninstall.

If cloud backup is added later, it must be separately designed as an encrypted backup feature.

# 41. SECURITY ACCEPTANCE CRITERIA

The feature is complete only when:

* [ ] App Lock uses Android biometric/device authentication.
* [ ] Fingerprint/biometric data is never stored by the application.
* [ ] Device PIN/password is never stored by the application.
* [ ] Sensitive documents are stored locally.
* [ ] Document images are encrypted.
* [ ] Sensitive structured data is encrypted.
* [ ] Encryption keys are protected by Android Keystore.
* [ ] Aadhaar/PAN are masked in normal UI.
* [ ] Full sensitive values require authentication.
* [ ] Backgrounding protects sensitive screens.
* [ ] Recent-app preview does not expose sensitive information.
* [ ] Normal app updates preserve the local encrypted vault.
* [ ] Database migrations preserve existing user data.
* [ ] Root/device integrity checks run before sensitive content is opened.
* [ ] Production has no root-detection bypass.
* [ ] Play Integrity is used where appropriate.
* [ ] Smart Fill cannot access the vault while locked.
* [ ] Smart Fill retrieves only the fields required.
* [ ] Temporary sensitive values are cleared after use.
* [ ] Sensitive data is not stored in ordinary shared storage.
* [ ] Sensitive data is not written to logs or analytics.

Integrate this security layer into the EXISTING Flutter application.

Do NOT rewrite unrelated features.

Priority:

```text
Device Integrity
       ↓
Biometric / Device Authentication
       ↓
Android Keystore
       ↓
Encrypted Local Vault
       ↓

       ↓

       ↓
Smart Fill Security
```

Use Android's official security primitives and maintained libraries.

Do not invent cryptography.

Do not store biometric/PIN data.

Do not create a hidden production security bypass.

The final application should behave like a secure personal document vault:

```text
Open App
   ↓
Security Check
   ↓
Fingerprint / Face / Device Credential
   ↓
Unlock Secure Vault
   ↓
View Documents
   ↓
Use Smart Fill only with approved data
```

```
### सबसे important architecture

**Aadhaar/PAN images:** app की **private encrypted local storage**
```
